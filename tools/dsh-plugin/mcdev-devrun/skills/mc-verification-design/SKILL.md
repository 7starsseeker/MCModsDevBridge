# 可验证性设计（mc-verification-design）

> 这套件真正的价值不是「能自动跑」，而是**把「这个功能要能用」翻译成机器可判定的步骤**。
> 本文是那层判断的方法：哪些能自动验、断言落在哪、时序怎么等、什么只能人眼看。

## 1. 判定的唯一来源：机器可读证据

一个好的判定，必须能回答「**谁证明了它**」。

| 证据 | 强度 | 说明 |
|---|---|---|
| 服务端侧回读（方块/背包/实体/玩家状态） | 最强 | 不依赖客户端自述，是权威口径 |
| 探针响应字段（`data.*` / `error.code`） | 强 | 结构化，可精确断言 |
| 日志文本（`text` / `textNot`） | 中 | 用来证明「拒绝加载」「断线原因」这类没有结构化出口的事 |
| 客户端 `/status` 自述 | 中 | 只能证明「客户端认为」，需服务端交叉验证 |
| 截图 | 弱（不进判定链） | 时机和判读都强相关于具体 mod，硬塞只会得到「拍了很多图但没人看」 |

**规则：客户端说「我做了」，要拿服务端回读才算数。** 「客户端说挖了」+「服务端 `/world/block` 是 air」
才是完整证据链；只有前半截等于没验。

## 2. 四类断言的适用边界

- **等值（`json`）**：枚举、布尔、数字。写实际类型，比较是「字符串化后相等」，不用担心 `true`/`"true"`。
- **包含（`contains`）**：列表、拼接文本、注册表 id 列表。别对列表用等值——顺序不稳定。
- **原始文本（`text`）**：日志尾部里的关键行（`HARD_DEP_NO_CANDIDATE`、`not white-listed`）。
- **不该出现（`textNot`）**：「这条不该发生」比「这条该发生」更容易写成脆的等值断言，用 `textNot` 表达。

反面：把整段日志写成等值断言（下一步日志加了一行就红）、拿 message 文案做断言（文案会改，`error.code` 才是契约）。

## 3. 时序：先 retry，再考虑 waitMs

- 有副作用的步骤（方块更新、掉落生成、动作栏显示、聊天到达）都可能慢一个 tick 到几秒。
- 用 `retry: {times, intervalMs}`（通过即早退）：快的时候不白等，慢的时候有上限。
- `waitMs` 只在「上一步的副作用必须先发生」时用一次；连续写多个 `waitMs` 是在用 sleep 掩盖时序问题。
- 定量取舍：服务端 tick 级副作用 20×250ms ≈ 5s 上限已足够；网络往返不需要 retry。

## 4. 「只对了一半」怎么表达

三种情况，三种写法，别混：

| 你想说的 | 写法 |
|---|---|
| 这条本来就该红（缺一半也算预期内） | 矩阵用例文件里 `expectFail: true` |
| A 应该生效、B 还不该生效 | 拆两条：A 绿、B 红且红的原因可读（不写成一条「大概对」的断言） |
| 这条今天做不到 | 写在用例 `note` 里，别写成永远绿的占位步骤 |

一个用例只表达一件事。红了以后能一眼看出是谁的问题，才算合格。

## 5. 把静默失败改成响亮失败

26.3 上有大量「返回成功但什么也没发生」（创造模式发物品包服务端不处理、`GameType.byName` 未知输入
静默回 SURVIVAL、空气处 pick 无动作）。设计接口/工具时：

- **能返回结构化错误就别返回 `ok:true`**：做不到就明说做不到（4xx + code），不要让上层以为成了。
- **能回读就别靠请求是否发出**：接口只说「包已发出」时，判定必须落在回读上。
- **必填参数、启动即校验**：把「静默地用了默认值」改成「启动就报错」，比养一条测试便宜。

## 6. 什么只能人眼看

- GUI 视觉/布局、光影与材质、动画与手感、音效、可玩性。
- 这些的自动化收益极低而维护成本极高。正确做法是 `-KeepRunning` 留下现场，
  由人（或 computer use 接管屏幕）去看，然后把「看到了什么」写成结论，而不是假装断言了它。
- 一个中间态：**能结构化的 UI 状态**（控件树、可见文本）可以断言——`/ui/snapshot` 就是为此存在的
  （`TitleScreen` 9 个控件、`OptionsScreen` 14 个控件这类）。视觉美观不行，控件存在/文本对不对可以。

## 7. 反模式清单

- 断言里写死玩家名（名字每次变 → 用 `{{player}}`）。
- 断言里写死端口（实例可配 → 读 `/status` 或登记）。
- 用一条步骤验两件事（红了看不出是谁）。
- 用 `sleep` 代替 `retry`（慢机器上必然翻车）。
- 用截图当判定（不进链，只当人看的辅助）。
- 用「跑完了没报错」当通过（无输出 ≠ 通过，必须有 `PASS=n FAIL=0 total=n` 这种可读的结论行）。

## 8. 自检问句

1. 这条断言，**谁**证明了它？证据在哪个字段/哪一行日志？
2. 如果实现坏了，这条会**静默变绿**还是立刻红？（会静默变绿 ⇒ 这条断言没价值）
3. 换台机器、换个玩家名、换个端口，这条还成立吗？
4. 这条红了，我第一眼能知道是自己的 mod 的问题还是环境问题吗？
