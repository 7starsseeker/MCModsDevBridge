# 多人语义怎么验：第二个玩家、广播、白名单（mc-multiplayer-verification）

给「这个功能只在多人才露馅」用的。命中词：多人、第二个玩家、旁观者、广播、聊天、白名单、在线模式、op、
两个客户端、端口冲突、alreadyInWorld。

## 0. 先认清套件的边界

编排脚本**一次只驱动一个客户端**（`devrun.ps1` 的 client 是单数），客户端探针端口默认 **39002**，
而 `-Family all` 三家共用这个端口 ⇒ **矩阵必须串行**。想同时跑两个客户端，第二个得你自己起，
并且**必须换一个探针端口**，否则两者抢 39002，后起的那个连不上、表现为「客户端没起来」。

所以：多人的**编排**是手工的，多人的**断言**才是套件擅长的部分。

## 1. 第一件事：让第二个人进得来

| 障碍 | 真相 |
|---|---|
| 白名单 | **默认开着**（见 `mc26-multiloader-traps`）。没加名字的人连上就被踢，日志看起来像「网络问题」 |
| 在线模式 | `online-mode=true` 时离线/重名客户端进不来；专用测试服通常设 `false` |
| op | 脚本会自动 op 第一个玩家；**第二个玩家默认不是 op**，用 `/command` 跑 op 指令前先确认 |
| 端口 | 服务端探针 39001、客户端探针 39002 是**探针**端口，和游戏端口（默认 25565/25566）不是一回事 |

`/connect` 的默认目标是 `127.0.0.1:25566`，**body 优先于 query**（两条都支持）。已在世界里时它返回
`alreadyInWorld:true` 并**直接返回、不重连**——想换服必须先 `/world/leave`（或 `/quit` 重启客户端），
否则你会对着旧连接发一堆请求还以为换成功了。

## 2. 服务端的三个「谁在」的问题，只有一个权威

| 入口 | 回答 | 权威性 |
|---|---|---|
| `/status` | `players`（人数）、`maxPlayers` | 服务端自己的计数，权威 |
| `/player/state?player=<名字>` | 该玩家的位置/维度/gamemode/血量；不在线报 `player not online` | **权威**（连「这个人在不在」都能直接问） |
| `/entity/list` | 实体列表 | 客户端那份是「我看到的」，服务端那份才可信 |

断言「A 进来了」就写 `/player/state?player=A` 的 `found`/位置，别写人数（人数会被上一轮残留玩家污染）。

## 3. 一个客户端也能验的多人语义

- **聊天能不能到服务端**：客户端 `/chat/send` → 服务端 `/log/tail` 找那行（服务端日志是权威）。
- **命令的权限边界**：`/command` 以控制台执行，**不是**以玩家身份执行 ⇒ 想验「普通玩家不能执行 op 指令」，
  得用客户端 `/command`（以玩家身份发）再断言回执/日志。
- **玩家数据的持久化**：断开/重连后 `/player/state` 的坐标、物品是否还在（用 `/player/inventory` 对照）。
- **广播/提示**：`/chat/tail` 有 `overlay` 字段，**actionbar 只有 `overlay:true` 才算**；
  真系统消息走另一个事件，别把 actionbar 当广播回执（同一个坑在 `mcdev-fixture-design` §2 记过）。

## 4. 真要两个客户端：手工拓扑

1. 建/复制第二个实例（`register-instance.ps1` + `provision-instance.ps1`），**改它的探针端口**（39002 → 39003）。
2. 起服务端（`devrun.ps1 -KeepRunning`，或已起着的测试服）。
3. 两个客户端各自起（`runClient`），各自 `/connect` 到同一台服。
4. 断言「B 看得到 A 说的话」：拿 **B 的** `/chat/tail` 断言，不是 A 的、也不是服务端的。
5. 收尾：两个客户端都要 `/quit`，39002/39003 都释放后 `gradlew` 才放手（脚本里等的是三个端口）。

两边**同时**发动作时注意：客户端动作（`/action/move` 等）只作用于自己的玩家；服务端动作要带
`player` 参数才是对那个人。

## 5. 边界（写进报告）

- **双客户端编排没有实跑过**：本仓只跑过「单客户端 + 服务端」，§4 是拓扑推演 + 单客户端已验证的端点组合。
- **能连上 ≠ mod 功能生效**：协议层不携带加载器信息，连不上说明协议/版本不对，连上了也不证明你的
  mod 的对端逻辑在跑——那是 `mcdev-fixture-design` 的握手判据管的事。
- **单人世界不能替代**：单人下客户端即服务端，所有「只有一侧存在」的现象都会消失。

## 6. 三个反模式

1. 用 `/entity/list` 里有个玩家实体当「他真在」——用 `/player/state?player=` 问。
2. 第二个客户端撞 39002 后，把「探针连不上」诊断成「客户端崩了」——先看端口，见 `mcdev-devrun` 的排障。
3. 只断言自己这一侧：多人的 bug 恰恰在「另一个人看不到」，断言必须落在**另一个人**的探针上。
